## 2. 产品约束

1. 保留现有一级菜单平铺结构，不做菜单收拢、角色模式切换或“专家模式”。
2. 业务人员具备 SQL 能力，数据库 SQL 编辑能力必须保留。
3. 变量、模型和规则的引用仍只通过稳定 ID 关联；输出引用继续使用 `ref_type` 区分类型。
4. 用户填写的编码、名称、导入字段和 SQL 原样保留，不做自动命名转换。
5. 本批只修复正确性和错误状态反馈，不混入决策表矩阵化、决策流布局重构、日志运营看板和项目级数据权限等后续子项目。

## 3. 问题与目标

本批解决五个已经通过真实页面和代码确认的问题：

1. 新建字段空白表单错误显示 `2/4 已就绪`。
2. 只打开已发布规则设计器也会自动创建生命周期草稿。
3. FIRST 决策表首次命中后，后续未执行规则被展示成条件或动作为空。
4. 模型列表把配置的 CUDA 展示成实际执行设备，掩盖 CPU 回退状态。
5. 规则测试在全项目范围难以区分同名规则，空的固定用例区域挤占首屏。

成功标准：页面展示必须与真实配置和运行状态一致；纯浏览不得写数据；状态未知时不得用默认值伪装成已知状态。

## 4. 总体设计

本批不引入新的持久化表和跨模块抽象。改动分别限定在已有边界内：

- 字段进度由 `VariableList.vue` 的配置检查计算和预览失效逻辑负责。
- 规则草稿由共享 `ruleDraftMixin.js` 和现有只读遮罩负责，所有设计器共享同一行为。
- 决策表追踪由 `TraceTree.vue` 组合静态 `modelJson` 与动态表达式追踪。
- 模型运行状态由现有 `runtimeCapabilities` 接口扩展，运行时会话管理器提供只读状态查询。
- 规则测试只调整选项标签和页面内容顺序，不改变执行接口及测试用例数据结构。

各修复互不依赖，可以分别编写失败测试和实现；最终再做一次真实 UI 串联验证。

## 5. 字段配置进度

### 5.1 就绪计算

四个步骤按依赖顺序计算：

1. `scopeReady`：已选择全局，或已选择项目级且存在项目 ID。
2. `definitionReady`：`scopeReady` 为真，且编码、名称、类型均有效。
3. `sourceReady`：`definitionReady` 为真，且当前来源的必填配置有效。
4. `validationReady`：`sourceReady` 为真，且无需在线预览，或当前配置已经成功预览。

因此空白 INPUT 字段为 `0/4`；补齐归属和定义后，INPUT 因无需额外来源配置和在线预览可达到 `4/4`。这表示没有遗漏的用户动作，不人为制造无意义步骤。

### 5.2 预览失效

API、DB、LIST 来源的以下信息变化时，必须将 `draftPreviewResult` 清空：

- 来源资源 ID；
- 参数映射、SQL、查询值、结果路径；
- 异常策略、回退值和影响取值结果的其他字段；
- 字段类型、作用范围或所属项目。

旧预览结果不得继续让“验证结果”保持完成。实现优先复用已有字段变更处理函数；只有无法集中处理的字段才增加精确 watcher，避免深度监听整个巨型表单。

### 5.3 错误反馈

预览失败保留失败信息，但步骤仍为未完成。切换来源时清空旧来源的预览结果和错误信息。

## 6. 规则草稿副作用

### 6.1 默认进入规则

- 存在 DRAFT：继续打开该 DRAFT，可编辑。
- 不存在 DRAFT，但存在已发布、已批准或已下线修订：加载该修订，只读展示。
- 只有旧版生效内容、没有治理修订：加载旧版内容，只读展示。
- 新建规则：后端创建规则时已经生成 DRAFT，行为保持不变。

`refreshViewedRevision()` 不再因为当前节点可派生草稿而主动调用创建接口。

### 6.2 显式开始编辑

共享只读遮罩提供“开始编辑”操作：

- 已发布、已批准或已下线修订：以当前修订 ID 为基线调用现有草稿创建接口。
- 旧版内容：用户点击后调用现有无基线草稿创建接口。
- 显式查看历史版本或历史修订：继续使用已有“派生草稿”接口，并保持来源校验。

创建成功后切换到新 DRAFT；创建失败或发生并发冲突时保持原节点只读，不清空已加载内容，并展示服务端错误。

### 6.3 数据兼容

- 不删除历史上自动创建的草稿。
- 不修改生命周期表结构和状态机。
- 页面刷新、路由进入、页签切换和退出设计器均不得创建草稿。

## 7. FIRST 决策表追踪

### 7.1 数据职责

- `definitionModel.rules` 是规则名称、条件、动作和排序的展示来源。
- 表达式追踪 AST 只提供是否执行、是否命中、实际取值和计算结果。
- 两者按编译器保持的规则顺序配对，不用名称或编码回溯引用。

### 7.2 状态判定

- 条件已执行且为真：`hit`，展示“命中”。
- 条件已执行且为假：`miss`，展示“未命中”。
- 条件节点或其父级分支 `evaluated=false`：`skipped`，展示“未执行（首次命中后终止）”。

解析器遇到未执行的 ELSE/IF 链仍保留对应静态规则，但不得从未执行 AST 推导空阈值、空条件或空动作。

### 7.3 兼容场景

至少覆盖首条命中、中间命中、无规则命中和默认规则命中。非 FIRST 策略保持现有语义，除非共用状态解析明确发现 `evaluated=false`。

## 8. 模型实际运行状态

### 8.1 接口扩展

保留 `/api/rule/model/runtimeCapabilities`，在现有全局能力字段之外增加：

```json
{
  "modelRuntimeStates": [
    {
      "modelId": 1,
      "configuredProvider": "CUDA",
      "effectiveProvider": "CPU",
      "state": "CPU_FALLBACK",
      "reason": "CUDA library load failed"
    }
  ]
}
```

允许的 `state`：

- `CPU`：模型配置为 CPU。
- `CUDA`：配置为 CUDA，且已有正常 CUDA 会话。
- `CPU_FALLBACK`：配置为 CUDA，运行时已经记录 CPU 回退。
- `NOT_INITIALIZED`：配置为 CUDA，但尚无 CUDA 会话或回退记录。
- `UNKNOWN`：无法可靠读取状态。

### 8.2 关联方式

`OnnxRuntimeSessionManager` 已按“模型 SHA-256 摘要 + 运行配置”保存会话和回退记录。新增只读查询方法，以 `rule_model.model_digest` 和解析后的 ONNX 配置查询状态；接口只返回模型 ID 和状态，不向前端暴露模型内容或摘要。

PMML 和非 ONNX 模型不生成 ONNX 运行状态。

### 8.3 页面展示

- 原“执行设备”列改名为“配置设备”。
- 新增“实际运行状态”列。
- `CPU_FALLBACK` 必须同时显示“已回退 CPU”和原因提示。
- `NOT_INITIALIZED` 显示“尚未初始化”，不得显示为 CUDA 已运行。
- 接口失败时显示“状态未知”，不得自动显示 CPU。

模型执行后重新加载列表或手动刷新时应反映最新回退状态。

## 9. 规则测试页

### 9.1 规则标识

全项目范围的规则标签统一为：

- 全局：`[全局] 规则名称 (规则编码)`；
- 项目级：`[项目名称 / 项目编码] 规则名称 (规则编码)`。

项目名称或编码缺失时只省略缺失部分，不显示 `undefined` 或空括号。限定到单一项目时仍可使用紧凑标签。

### 9.2 页面顺序

选中规则后的顺序调整为：

1. 规则摘要和上下文提示；
2. 输入参数；
3. 固定测试用例；
4. 执行结果和追踪。

没有固定测试用例时展示一行紧凑空状态和“收藏当前输入”入口，不保留大高度容器。有测试用例或批量结果时正常展开现有内容。

### 9.3 兼容性

不修改测试执行、场景收藏、批量执行、Diff、追踪和超时配置接口。

## 10. 错误处理

1. 所有只读状态查询失败都显示“未知/加载失败”，不使用可能误导用户的默认成功状态。
2. 草稿创建失败不改变当前查看节点，不丢失设计器内容。
3. 异步请求继续使用现有请求序号或来源键，过期响应不得覆盖当前页面。
4. 前端只展示经过裁剪的运行时错误摘要；完整堆栈仅留在服务端日志。
