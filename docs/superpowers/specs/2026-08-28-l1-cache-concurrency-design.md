# L1MemoryCache 并发优化设计

## 1. 目标

让高频缓存读取不再争用写锁，同时保持全量同步、增量推送、删除和清空之间的原子语义。

## 2. 当前语义

- `get()`、`put()`、`remove()`、`clear()`、`size()`、`getVersions()` 和 `replaceSnapshot()` 全部进入 `cacheLock`。
- 底层容器已经是 `ConcurrentHashMap`，但高频读取仍被串行化。
- `replaceSnapshot()` 在锁内构建并替换新映射，因此同时到达的增量 `put()` 会等待快照提交，随后写入新映射。现有测试依赖这一语义。

## 3. 新并发模型

```text
读取路径：volatile map 引用 -> ConcurrentHashMap.get/size/forEach
写入路径：cacheLock -> 读取当前 map 引用 -> 修改或替换 -> 解锁
```

- `cache` 改为 `volatile ConcurrentHashMap<String, CachedRule>`。
- `get()` 直接从当前引用读取，不加锁。
- `size()` 直接读取当前引用。
- `getVersions()` 先复制一次当前引用，再遍历该映射；结果是调用期间的弱一致快照，允许并发增量更新。
- `put()`、`remove()`、`clear()` 继续在 `cacheLock` 内修改当前映射。
- `replaceSnapshot()` 继续在 `cacheLock` 内完成快照构建和引用替换，保证构建期间到达的增量写入不会落在即将被替换的旧映射。

本轮不把写锁替换为读写锁。读路径完全不加锁后，读写锁没有额外收益。

## 4. 容量限制

- 保留当前 `maxSize` 行为和重复规则覆盖语义。
- 本轮不改变任意首键淘汰策略，避免把并发修复扩大成缓存策略重写。
- 构造参数必须大于零；若当前实现未校验，新增显式参数校验。

## 5. 测试

1. 现有“全量快照删除缺失规则”测试继续通过。
2. 现有“增量写等待快照提交并写入新映射”测试继续通过。
3. 新增“快照构建阻塞时，`get()` 仍能读取旧快照且不会等待”测试。旧实现必须在该测试上失败。
4. 新增读写压力测试：多个读线程与快照/增量写线程并发运行，不出现异常、空引用或丢失快照提交后的增量。
5. 新增非法 `maxSize` 参数测试。

并发测试以 `CountDownLatch` 和明确的线程完成条件为主，不用脆弱的微秒级耗时断言。

## 6. 性能测量

提供独立的本地基准入口，对比修改前后的：

- 单线程缓存命中吞吐。
- 8、32、128 个并发读线程吞吐。
- 全量快照提交期间的读取延迟。

基准结果写入构建目录，不提交机器相关的绝对阈值。验收重点是读取不再因写锁出现队头阻塞。

## 7. 非目标

- 不引入第三方缓存库。
- 不改变缓存键、规则版本或服务端同步协议。
- 不在本轮实现 LRU/LFU。
